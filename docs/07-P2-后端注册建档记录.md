# P2 后端注册建档记录

## 1. 本次目标

本次推进范围是 P2-B 和 P2-C：

1. 建立志愿者档案和审核记录的后端实体、Mapper、Service。
2. 改造注册流程，使注册成功后自动绑定志愿者角色并创建待审核档案。
3. 验证注册建档链路真实可运行。

本次不做用户端资料页面、管理端志愿者审核页面、活动报名和二维码签到签退。

## 2. 后端新增内容

### 2.1 注册扩展点

新增：

```text
ruoyi-framework/src/main/java/com/ruoyi/framework/web/service/RegisterUserPostProcessor.java
```

作用：

1. 框架层继续负责账号注册。
2. 业务模块通过实现该接口，补充注册后的业务数据。
3. 避免把志愿业务表写死在 RuoYi 系统用户模块里。

`SysRegisterService.register` 已增加事务和后置处理逻辑：

1. 校验用户名、密码、验证码。
2. 写入 `sys_user`。
3. 调用注册后置处理器。
4. 志愿模块写入角色、档案和审核记录。
5. 整个注册链路在同一事务中提交。

## 3. 关键实现说明

### 3.1 为什么不直接改 `SysUserService`

`SysUserService` 是系统用户模块，适合维护账号、角色、部门、岗位等基础能力。如果把志愿者档案写进该模块，会让系统模块和业务模块耦合过紧。

当前做法是：

1. `SysRegisterService` 提供注册后置扩展点。
2. `voluntary-system` 实现扩展点。
3. 志愿业务只在业务模块中维护自己的表。

这样后续扩展活动、报名、签到签退时，业务边界仍然清晰。

### 3.2 事务边界

注册链路需要保证一致性：

```text
sys_user
sys_user_role
vol_volunteer_profile
vol_audit_record
```

以上写入必须同时成功。若角色未初始化、档案插入失败或审核记录插入失败，应回滚账号注册，避免出现“有账号但没有档案”的脏数据。

### 4.2 运行级注册建档冒烟

验证环境：

| 服务 | 地址 |
| --- | --- |
| 后端 | `http://127.0.0.1:8080` |
| MySQL | `127.0.0.1:33306` |
| Redis | `127.0.0.1:6379` |

验证步骤：

1. 启动项目内临时 MySQL。
2. 导入 `sql/ruoyi_voluntary.sql`。
3. 启动后端 Jar，并覆盖数据源端口为 `33306`。
4. 调用注册接口：

```bash
curl -s -X POST http://127.0.0.1:8080/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"p2vol125","password":"123456"}'
```

接口返回：

```json
{"msg":"操作成功","code":200}
```

数据库验证查询结果：

```text
user_id  user_name  role_key   profile_status  total_minutes  service_count  target_type  audit_status  audit_reason
2        p2vol125   volunteer  0               0              0              volunteer    0             志愿者注册后进入待审核状态
```

结论：

1. 注册成功后已写入 `sys_user`。
2. 已绑定 `volunteer` 角色。
3. 已创建 `vol_volunteer_profile`。
4. 档案状态为 `0 待审核`。
5. 已写入 `vol_audit_record` 初始审核记录。
6. 运行日志显示上述写入处于同一事务中。

验证完成后，后端和临时 MySQL 均已关闭，端口 `8080`、`33306` 已释放。
