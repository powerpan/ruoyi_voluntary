# 参考项目复用分析

## 1. 分析目的

本文档用于分析参考项目 `/Users/ericpan/game_project/ruoyi_pet_adopt` 中哪些内容适合复用到“志愿活动管理系统”，哪些内容必须重写，以及迁移时应遵守的边界。

当前项目 `ruoyi_voluntary` 目前仅有需求说明文档，还没有工程代码。因此参考项目更适合作为工程骨架来源，而不是作为业务代码直接复制对象。

## 2. 参考项目概况

参考项目是基于 RuoYi + Vue 的课程项目版宠物领养平台，当前已压缩为围绕“发布领养、审核、申请、沟通、确认、回访”的主业务闭环。

参考项目主要目录如下：

| 目录 | 作用 | 是否建议复用 |
| --- | --- | --- |
| `ruoyi-admin` | 后端启动模块、通用控制器、配置文件 | 建议复用 |
| `ruoyi-common` | RuoYi 通用工具、分页、返回对象、安全工具 | 建议复用 |
| `ruoyi-framework` | Spring Security、Token、验证码、拦截器 | 建议复用 |
| `ruoyi-system` | 系统用户、角色、菜单、字典、日志 | 建议复用 |
| `pet-system` | 宠物领养业务模块 | 改造为 `voluntary-system` |
| `ruoyi-ui` | 管理端 Vue2 + Element UI | 建议复用后改页面 |
| `pet-app` | 用户端 Vue2 前台应用 | 建议复用后改页面 |
| `sql` | 初始化数据库、菜单、演示数据 | 建议按志愿业务重写 |
| `deploy` | Docker 部署结构 | 可后期复用 |
| `start-dev.command` | 本地三端启动脚本 | 可改造 |
| `stop-dev.command` | 本地停止脚本 | 可改造 |

## 3. 可直接复用的工程能力

### 3.1 后端基础能力

以下能力与业务无关，适合保留：

1. 登录、退出、Token 认证。
2. 验证码和 Redis 缓存。
3. 用户、角色、菜单、岗位、部门、字典管理。
4. 操作日志、登录日志、在线用户、服务监控。
5. 通用分页、统一返回对象、异常处理。
6. 文件上传、头像上传、静态资源访问。
7. MyBatis Plus 的实体、Mapper、分页查询模式。
8. `@PreAuthorize` 权限控制和 RuoYi 菜单权限模型。

### 3.2 前端基础能力

管理端可复用：

1. 登录页、验证码、权限路由。
2. Layout、侧边菜单、标签页、面包屑。
3. 表格分页、筛选栏、弹窗表单、状态标签。
4. 字典标签、图片上传、导出按钮模式。
5. 操作日志、系统管理等 RuoYi 原生页面。

志愿者端可复用：

1. 登录、注册、验证码、Token 存储。
2. 首页布局、顶部导航、底部版权。
3. 活动列表和详情页的前台页面结构。
4. 个人中心、头像、资料编辑页面模式。
5. 通知中心页面模式。

### 3.3 脚本与部署能力

参考项目的本地启动脚本有三端启动逻辑：

1. 后端：`ruoyi-admin`
2. 管理端：`ruoyi-ui`
3. 用户端：`pet-app`

当前项目可以改造为：

1. 后端：`ruoyi-admin`
2. 管理端：`ruoyi-ui`
3. 志愿者端：`voluntary-app`

数据库和环境变量需要统一替换为 `RUOYI_VOLUNTARY_*`。

## 4. 业务模块映射

宠物领养业务不能原样保留，但它的结构可以映射到志愿活动业务。

| 参考项目对象 | 当前项目对象 | 复用建议 |
| --- | --- | --- |
| `pet-system` | `voluntary-system` | 复制模块结构后整体改名 |
| `PetAppController` | `VolunteerAppController` | 保留用户端控制器思路，业务方法重写 |
| `PetManagerController` | `VolunteerManagerController` | 保留管理端控制器思路，业务方法重写 |
| `PetBaseDomain` | `VolunteerBaseDomain` | 可直接复用审计字段基类 |
| `pet_user_profile` | `vol_volunteer_profile` | 改为志愿者档案和审核状态 |

| `pet_adoption_application` | `vol_activity_signup` | 改为活动报名表 |

## 5. 不建议直接复用的内容

以下内容与志愿活动主题不匹配，不应保留在最终系统中：

1. 宠物档案、物种、品种、绝育、健康状态等字段。
2. 领养申请中的居住情况、养宠经验、领养承诺等字段。
3. 看宠预约、领养确认、回访计划等流程。
4. 宠物图片、宠物主题 logo、宠物页面文案。
5. 宠物相关菜单、权限标识和字典。
6. 领养发布方与申请方双向沟通流程，除非后续明确要做活动留言。

## 6. 当前项目需要新增的关键能力

参考项目没有以下志愿业务能力，需要重新实现：

### 6.1 志愿者审核

参考项目的普通注册只创建 `sys_user`，不完整创建业务档案，也没有“待审核志愿者不能报名”的规则。

当前项目需要：

1. 注册时创建 `sys_user`。
2. 同时创建 `vol_volunteer_profile`。
3. 默认审核状态为 `0 待审核`。
4. 未审核通过不能报名活动，不能签到签退。
5. 管理员审核后写入审核记录和通知。

### 6.2 二维码签到签退

参考项目没有二维码签到签退能力。

当前项目需要新增：

1. 活动二维码令牌表。
2. 签到二维码生成接口。
3. 签退二维码生成接口。
4. 二维码有效期校验。
5. 报名通过校验。
6. 重复签到、重复签退、未签到先签退拦截。
7. 异常签到签退记录。

### 6.3 服务时长统计

参考项目没有服务时长计算模型。

当前项目需要新增：

1. 签到签退记录。
2. 服务记录。
3. 时长计算规则。
4. 最大可计入时长规则。
5. 异常记录人工修正。
6. 按志愿者、活动、组织、时间范围统计。

## 7. 迁移策略

迁移时建议按以下顺序执行：

1. 复制参考项目基础工程到当前仓库。
2. 将项目名改为 `ruoyi-voluntary`。
3. 将 `pet-system` 改名为 `voluntary-system`。
4. 暂时删除或隔离宠物业务页面和 SQL，保留基础框架可启动。
5. 建立新的志愿业务 SQL 和菜单。
6. 先实现志愿者档案，再实现活动，再实现报名，再实现签到签退。
7. 每完成一个阶段都运行编译和构建验证。

## 8. 迁移风险

| 风险 | 影响 | 应对方式 |
| --- | --- | --- |
| 大量宠物命名残留 | 论文和演示不专业 | P1 阶段专门做命名清理验收 |
| 菜单和页面不一致 | 后台点击 404 | SQL 菜单必须和 `ruoyi-ui/src/views` 对齐 |
| 注册逻辑只创建系统用户 | 志愿者审核链断开 | P2 改造注册服务，创建志愿者档案 |
| 签到签退并发重复 | 服务时长不准确 | 数据库唯一索引和状态条件更新 |
| 二维码长期有效 | 存在代签风险 | 令牌有效期、活动绑定、操作类型绑定 |
| 一次改太多 | 无法定位错误 | 严格按阶段提交和验证 |

## 9. 本阶段结论

参考项目适合作为工程底座，尤其适合复用 RuoYi 基础模块、管理端页面模式、用户端页面结构、业务模块拆分方式、SQL 初始化方式和启动部署脚本。

但当前项目的核心业务不是领养，而是志愿活动管理。因此应采用“骨架复用、业务重写”的策略。第一轮代码阶段只应完成工程迁移和命名改造，不应同时实现全部业务。
