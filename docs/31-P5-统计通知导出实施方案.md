# P5 统计、通知与导出实施方案

## 1. 阶段目标

P5 的目标是在 P4 已完成的“注册审核 -> 活动发布 -> 报名筛选 -> 二维码签到签退 -> 服务记录生成”闭环基础上，补齐管理效率能力：

1. 管理端统计总览：展示志愿者、活动、报名、签到签退、服务时长等核心指标。
2. 服务时长统计：按活动、志愿者、组织和时间范围统计服务分钟数、服务次数和排行。
3. 通知中心：把审核结果、报名筛选结果、签到异常和服务时长确认等业务事件沉淀为站内通知。
4. 数据导出：导出志愿者档案、报名名单、签到签退记录和服务记录。
5. 阶段验收：验证统计口径、通知投递、导出文件和测试数据清理。

P5 仍然按子阶段推进，不一次性实现全部统计、通知和导出代码。

## 3. 阶段边界

### 3.1 本阶段实现

1. 新增业务通知表 `vol_notification`，支持用户个人站内通知和已读状态。
2. 新增统计查询 DTO/VO 和 Mapper 查询，不新增统计缓存表。
3. 新增管理端统计接口和统计页面。
4. 新增用户端通知接口和通知中心页面。
5. 在志愿者审核、报名筛选、签到/服务异常等业务动作中写入通知。
6. 新增管理端导出接口和页面导出按钮。
7. 补齐 P5 阶段验收记录。

### 3.2 本阶段不实现

1. 短信、邮件、微信、App 推送等外部消息通道。
2. 异步导出任务队列和大文件离线下载。
3. 复杂 BI 图表、地图热力图、跨年报表。
4. 组织管理员数据权限隔离。
5. 服务证明 PDF 或证书生成。
6. 动态二维码、定位签到等 P4 扩展能力。

这些能力可作为 P6 后的增强项，不放入当前课程项目主线。

## 4. 统计设计

### 4.1 统计口径

| 指标 | 口径 |
| --- | --- |
| 志愿者总数 | `vol_volunteer_profile` 全量记录数 |
| 审核通过志愿者数 | `audit_status = 1` |
| 活动总数 | `vol_activity` 全量记录数 |
| 已发布活动数 | `status = 1` |
| 报名总数 | `vol_activity_signup` 全量记录数 |
| 已通过报名数 | `vol_activity_signup.status = 1` |
| 签到人数 | `vol_checkin_record.checkin_time is not null` |
| 签退人数 | `vol_checkin_record.status = 1` |
| 有效服务记录数 | `vol_service_record.status = 1` |
| 有效服务分钟数 | `sum(vol_service_record.service_minutes) where status = 1` |
| 异常服务记录数 | `vol_service_record.status = 2` 或 `vol_checkin_record.status = 2` |

统计时间范围默认按 `service_date` 或业务创建时间过滤：

1. 服务时长类指标优先使用 `vol_service_record.service_date`。
2. 报名类指标使用 `vol_activity_signup.create_time`。
3. 活动类指标使用 `vol_activity.start_time` 或 `create_time`，页面需要明确筛选字段。
4. 签到类指标使用 `vol_checkin_record.checkin_time`。

## 5. 通知设计

### 5.1 数据表 `vol_notification`

P5-A 新增业务通知表，不复用 `sys_notice`。原因：

1. `sys_notice` 面向系统公告，缺少接收人、已读时间和业务对象字段。
2. 志愿者端需要“只看我的通知”。
3. 审核、报名、签到和服务记录通知需要关联业务对象。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint PK | 主键 |
| `receiver_user_id` | bigint | 接收人用户 ID |
| `actor_user_id` | bigint | 触发人用户 ID，可为空 |
| `notice_type` | varchar(32) | 通知类型 |
| `target_type` | varchar(32) | 业务对象类型 |
| `target_id` | bigint | 业务对象 ID |
| `title` | varchar(160) | 通知标题 |
| `content` | varchar(1000) | 通知内容 |
| `action_url` | varchar(255) | 用户端跳转地址 |
| `status` | tinyint | `0未读 1已读` |
| `read_time` | datetime | 阅读时间 |
| `create_by` | varchar(64) | 创建人 |
| `create_time` | datetime | 创建时间 |
| `update_by` | varchar(64) | 更新人 |
| `update_time` | datetime | 更新时间 |
| `remark` | varchar(500) | 备注 |

建议索引：

1. `idx_notification_receiver_status(receiver_user_id, status, create_time)`
2. `idx_notification_target(target_type, target_id)`
3. `idx_notification_type(notice_type, create_time)`

### 5.2 通知类型

字典 `vol_notification_type`：

| 值 | 名称 | 触发场景 |
| --- | --- | --- |
| `volunteer_audit` | 志愿者审核 | 管理员通过、驳回、禁用、启用档案 |
| `signup_review` | 报名筛选 | 报名通过、拒绝、候补 |
| `activity_change` | 活动变更 | 活动取消、下架、结束 |
| `checkin_abnormal` | 签到异常 | 未签退、异常记录、人工确认 |
| `service_record` | 服务记录 | 服务记录生成、修正、作废 |
| `system` | 系统消息 | 后续手工通知或公告 |

字典 `vol_notification_status`：

| 值 | 名称 |
| --- | --- |
| `0` | 未读 |
| `1` | 已读 |

### 5.3 用户端通知接口

接口前缀：`/app/voluntary/notifications`

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/mine` | 我的通知列表 |
| `GET` | `/unread-count` | 未读数量 |
| `PUT` | `/{id}/read` | 标记单条已读 |
| `PUT` | `/read-all` | 全部标记已读 |

接口规则：

1. 只能读取和修改当前登录用户自己的通知。
2. 通知列表按 `create_time desc` 排序。
3. 已读操作必须校验 `receiver_user_id = currentUserId`。
4. 通知跳转地址只允许用户端内部路由，如 `/signups`、`/service-records`、`/me`。

### 5.4 管理端通知接口

接口前缀：`/manager/voluntary/notifications`

| 方法 | 路径 | 说明 | 权限 |
| --- | --- | --- | --- |
| `GET` | `/list` | 通知记录列表 | `manager:voluntary:notification:list` |
| `GET` | `/{id}` | 通知详情 | `manager:voluntary:notification:query` |

P5 首版管理端只做查询，不做手工群发，避免引入消息审核和误发风险。

## 6. 导出设计

### 6.1 复用方式

导出复用 RuoYi 系统模块现有模式：

1. Controller 使用 `HttpServletResponse`。
2. 方法加 `@Log(title = "...", businessType = BusinessType.EXPORT)`。
3. 方法加 `@PreAuthorize` 权限控制。
4. 查询当前筛选条件下的完整列表。
5. 使用 `ExcelUtil<T>` 输出 Excel。
6. 前端使用 `this.download(url, params, filename)`。

### 6.2 导出接口

接口前缀：`/manager/voluntary`

| 方法 | 路径 | 数据 | 权限 |
| --- | --- | --- | --- |
| `POST` | `/volunteers/export` | 志愿者档案 | `manager:voluntary:volunteer:export` |
| `POST` | `/signups/export` | 报名名单 | `manager:voluntary:signup:export` |
| `POST` | `/checkins/export` | 签到签退记录 | `manager:voluntary:checkin:export` |
| `POST` | `/service-records/export` | 服务记录 | `manager:voluntary:serviceRecord:export` |
| `POST` | `/statistics/service-records/export` | 统计后的服务明细 | `manager:voluntary:statistics:export` |

### 6.3 导出字段

志愿者档案：

1. 账号、真实姓名、性别、手机号、组织、学院班级。
2. 审核状态、审核意见。
3. 累计服务分钟数、服务次数。
4. 创建时间、更新时间。

报名名单：

1. 活动标题、志愿者姓名、手机号、组织。
2. 报名理由、经验。
3. 报名状态、筛选意见、筛选人、筛选时间。
4. 报名时间。

签到签退记录：

1. 活动标题、服务地点、志愿者姓名、手机号、组织。
2. 活动时间、签到时间、签退时间。
3. 签到方式、签退方式、状态、异常原因。

服务记录：

1. 活动标题、服务地点、志愿者姓名、手机号、组织。
2. 服务日期、计入开始时间、计入结束时间。
3. 服务分钟数、状态、来源签到记录 ID。
4. 修正原因、生成时间。

## 7. 页面设计

### 7.1 管理端统计页面

路径：`/voluntary/statistics`

页面结构：

1. 顶部筛选区：日期范围、活动、组织、志愿者姓名。
2. 总览卡片：志愿者数、活动数、报名数、签到签退数、服务分钟数、异常数。
3. 活动统计表：报名、通过、签到、签退、服务时长。
4. 志愿者排行表：服务次数、服务分钟数、最近服务日期。
5. 组织统计表：组织人数、服务次数、服务分钟数。
6. 简单趋势图：按日或按月展示服务分钟数。

首版图表可复用 `echarts`，但页面要保持管理工具风格，避免做成营销大屏。

### 7.2 管理端通知记录页面

路径：`/voluntary/notification`

页面结构：

1. 按接收人、通知类型、状态、创建时间查询。
2. 展示标题、接收人、类型、业务对象、状态、创建时间。
3. 查看详情弹窗。
4. 首版不提供手工发送、删除或批量重发。

### 7.3 用户端通知中心

路径：`/notifications`

页面结构：

1. 顶部显示未读数量。
2. 按全部/未读/已读筛选。
3. 按通知类型筛选。
4. 通知卡片展示标题、内容摘要、时间、状态和跳转入口。
5. 支持单条已读和全部已读。

## 10. 验收标准

P5 完成时必须证明：

1. 管理端统计总览能展示当前库的核心指标。
2. 活动维度统计与活动报名、签到、服务记录数据一致。
3. 志愿者维度统计与 `vol_service_record.status = 1` 的有效服务记录一致。
4. 用户端通知中心能看到自己的审核和报名通知。
5. 用户不能读取或标记他人的通知。
6. 管理端能查询通知记录。
7. 志愿者、报名、签到签退、服务记录导出均能下载 Excel。
8. 导出接口有权限控制和操作日志。
9. 验收临时数据清理后不影响 P3/P4 必要演示数据。
