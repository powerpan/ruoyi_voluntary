## 5. 核心状态设计

### 5.1 志愿者审核状态

| 状态值 | 含义 | 说明 |
| --- | --- | --- |
| `0` | 待审核 | 注册后默认状态 |
| `1` | 审核通过 | 可报名、签到签退 |
| `2` | 审核驳回 | 可修改资料后重新提交 |
| `3` | 禁用 | 管理员限制使用 |

### 5.2 活动状态

| 状态值 | 含义 | 说明 |
| --- | --- | --- |
| `0` | 草稿 | 管理端保存但用户端不可见 |
| `1` | 已发布 | 用户端可浏览和报名 |
| `2` | 已结束 | 活动已结束 |
| `3` | 已下架 | 管理员主动下架 |
| `4` | 已取消 | 活动取消 |

### 5.3 报名状态

| 状态值 | 含义 | 说明 |
| --- | --- | --- |
| `0` | 待筛选 | 志愿者已提交申请 |
| `1` | 已通过 | 可参与签到签退 |
| `2` | 已拒绝 | 不允许参与 |
| `3` | 候补 | 等待名额 |
| `4` | 已取消 | 志愿者取消报名 |

### 5.4 签到和服务记录状态

| 对象 | 状态值 | 含义 |
| --- | --- | --- |
| 签到记录 | `0` | 已签到未签退 |
| 签到记录 | `1` | 已签退 |
| 签到记录 | `2` | 异常 |
| 服务记录 | `1` | 有效 |
| 服务记录 | `2` | 异常 |
| 服务记录 | `3` | 作废 |

## 6. 关键实现说明

### 6.1 注册后自动建档

系统复用 RuoYi 注册逻辑创建 `sys_user` 账号，再在同一事务内创建 `vol_volunteer_profile` 待审核档案，并绑定 `volunteer` 角色。这样可以保证“账号、角色、档案”三者一致，避免出现有账号但无法进入志愿业务的脏数据。

### 6.2 活动报名与筛选

志愿者报名前需要通过以下校验：

1. 当前用户已登录。
2. 当前用户存在志愿者档案。
3. 档案审核状态为通过。
4. 活动处于已发布状态。
5. 报名时间在允许范围内。
6. 同一活动不能重复报名。

管理员筛选通过时，系统同步维护活动已通过人数，保证招募人数限制可以被持续校验。

### 6.3 二维码签到签退

二维码不直接暴露数据库主键，而是使用 `vol_activity_qr_token.token` 作为扫码入口参数。系统根据 token 找到活动和操作类型，再校验报名状态、重复签到、重复签退、未签到先签退等边界条件。

### 6.4 服务时长计算

系统以签到时间和签退时间计算服务分钟数。如果活动配置了最大可计入分钟数，则最终服务时长不超过该上限。签退成功后自动生成服务记录，并同步更新志愿者档案中的累计服务分钟数和服务次数。

### 6.5 站内通知

系统在志愿者审核、报名筛选、服务记录生成等业务节点写入 `vol_notification`。用户端只允许当前用户读取自己的通知，管理端可按条件查询通知记录。

### 6.6 导出

管理端在志愿者、报名、签到签退、服务记录四类页面提供导出按钮，后端使用 RuoYi `ExcelUtil` 生成 `.xlsx` 文件。

## 10. 已知不足与展望

当前项目定位是课程项目和毕业设计可演示系统，已覆盖核心业务闭环。后续可继续增强：

1. 接入短信、邮件或微信通知。
2. 使用动态二维码定时刷新，降低截图代签风险。
3. 增加组织管理员数据权限隔离。
4. 增加服务证明 PDF 生成。
5. 增加地图定位、现场码和后台人工补签审批。
6. 增加自动化端到端测试脚本。
7. 增加 Docker 部署流水线和线上环境监控。

论文中应把这些内容写入“展望”，不要把未实现能力描述成已完成能力。
