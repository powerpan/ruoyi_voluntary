# P2 志愿者账号与档案实施方案

## 1. 阶段目标

P2 的目标是完成“志愿者账号与档案”这条基础链路，为后续活动报名、签到签退和服务时长统计提供可依赖的用户身份和审核状态。

本阶段完成后，系统应支持：

1. 志愿者注册账号后自动生成志愿者档案。
2. 志愿者登录后可以查看和维护个人资料。
3. 新注册志愿者默认处于待审核状态。
4. 管理员可以查询、审核、驳回、禁用和启用志愿者。
5. 志愿者审核状态可以被后续报名接口复用。
6. 每次审核动作都有记录可追溯。

## 2. 现状分析

当前 P1 骨架已经完成，账号相关能力来自 RuoYi 默认实现。

可复用内容：

| 能力 | 现有位置 | P2 复用方式 |
| --- | --- | --- |
| 注册接口 | `POST /register` | 保留入口，注册成功后补建志愿者档案 |
| 登录接口 | `POST /login` | 保留，不在 P2 改认证机制 |
| 当前用户信息 | `GET /getInfo`、`GET /getUserProfile` | 继续返回基础用户信息，后续补充志愿者档案 |
| 用户资料更新 | `PUT /updateUserProfile` | 保留基础昵称、手机、邮箱更新 |
| 管理端用户体系 | `sys_user`、`sys_role`、`sys_menu` | 继续作为账号、角色和权限底座 |
| 用户端个人中心 | `voluntary-app/src/views/me/profile` | 作为志愿者资料维护页面的改造入口 |

需要新增内容：

| 能力 | 原因 |
| --- | --- |
| 志愿者档案表 | `sys_user` 只表示账号，不适合保存实名资料、组织、特长和服务统计 |
| 审核记录表 | 审核通过、驳回、禁用等动作需要留痕 |
| 志愿者资料接口 | 用户端需要读取和保存业务档案，而不是只更新系统用户字段 |
| 管理端志愿者审核接口 | 管理员需要独立管理志愿者档案 |
| 审核状态校验方法 | P3 报名接口需要判断是否具备报名资格 |

## 3. P2 边界

本阶段只处理账号、档案和审核，不提前实现活动业务。

P2 包含：

1. `vol_volunteer_profile` 表。
2. `vol_audit_record` 表。
3. 注册后自动创建志愿者档案。
4. 用户端个人资料查看和维护。
5. 管理端志愿者列表和审核操作。
6. 审核状态展示和后续报名资格校验方法。

P2 不包含：

1. 活动创建、发布和浏览。
2. 活动报名和报名筛选。
3. 二维码签到签退。
4. 服务记录生成和时长统计。
5. 数据导出和统计看板。

## 4. 数据库设计落地

### 4.1 志愿者档案表

表名：`vol_volunteer_profile`

关键字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 档案主键 |
| `user_id` | 关联 `sys_user.user_id`，唯一 |
| `real_name` | 真实姓名 |
| `gender` | 性别，沿用 `sys_user_sex` 字典值 |
| `id_card` | 证件号 |
| `phone` | 联系电话 |
| `organization` | 所属组织 |
| `major_or_class` | 学院班级或社区分组 |
| `specialty` | 服务特长 |
| `emergency_contact` | 紧急联系人 |
| `emergency_phone` | 紧急联系电话 |
| `audit_status` | 审核状态，`0待审核 1通过 2驳回 3禁用` |
| `audit_reason` | 审核意见 |
| `auditor_id` | 审核人 ID |
| `auditor_name` | 审核人姓名快照 |
| `audit_time` | 审核时间 |
| `total_service_minutes` | 累计有效服务分钟数，P5 统计时更新 |
| `service_count` | 有效服务次数，P5 统计时更新 |

索引：

1. `uk_volunteer_user(user_id)`
2. `idx_volunteer_audit(audit_status, create_time)`
3. `idx_volunteer_phone(phone)`

### 4.2 审核记录表

表名：`vol_audit_record`

关键字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 审核记录主键 |
| `auditor_id` | 审核人 ID |
| `auditor_name` | 审核人姓名快照 |
| `target_type` | 目标类型，P2 使用 `volunteer` |
| `target_id` | 目标业务 ID，P2 对应志愿者档案 ID |
| `target_user_id` | 目标用户 ID |
| `before_status` | 操作前状态 |
| `audit_status` | 操作后状态 |
| `audit_reason` | 审核意见或处理原因 |
| `create_time` | 操作时间 |

索引：

1. `idx_audit_target(target_type, target_id)`
2. `idx_audit_user(target_user_id)`
3. `idx_audit_time(create_time)`

## 5. 接口设计

### 5.1 用户端接口

接口前缀：`/app/voluntary`

| 方法 | 路径 | 功能 | 说明 |
| --- | --- | --- | --- |
| `GET` | `/profile` | 查看我的志愿者档案 | 返回 `sys_user` 基础信息和 `vol_volunteer_profile` |
| `PUT` | `/profile` | 修改我的志愿者档案 | 待审核或驳回状态允许修改实名资料 |
| `GET` | `/profile/audit-status` | 查看审核状态 | 用户端首页和个人中心可复用 |

规则：

1. 用户只能访问自己的志愿者档案。
2. 审核通过后仍可修改联系电话、特长等非关键字段。
3. 审核通过后修改真实姓名、证件号等关键字段时，建议重新变为待审核；若课程项目范围需要收敛，可先只允许管理员修改关键字段。
4. 禁用状态下用户可登录查看原因，但不能报名活动。

### 5.2 管理端接口

接口前缀：`/manager/voluntary`

| 方法 | 路径 | 功能 | 权限标识 |
| --- | --- | --- | --- |
| `GET` | `/volunteers/list` | 志愿者分页列表 | `manager:voluntary:volunteer:list` |
| `GET` | `/volunteers/{id}` | 志愿者详情 | `manager:voluntary:volunteer:query` |
| `PUT` | `/volunteers/{id}` | 管理员编辑档案 | `manager:voluntary:volunteer:edit` |
| `POST` | `/volunteers/{id}/audit` | 通过或驳回 | `manager:voluntary:volunteer:audit` |
| `PUT` | `/volunteers/{id}/status` | 禁用或启用 | `manager:voluntary:volunteer:edit` |
| `GET` | `/volunteers/{id}/audit-records` | 查看审核记录 | `manager:voluntary:volunteer:query` |

### 6.2 核心类

| 类 | 说明 |
| --- | --- |
| `VolVolunteerProfile` | 志愿者档案实体 |
| `VolAuditRecord` | 审核记录实体 |
| `VolVolunteerProfileMapper` | 档案持久层 |
| `VolAuditRecordMapper` | 审核记录持久层 |

| `VolunteerRegisterSupport` | 注册后创建档案的支撑服务，可直接并入档案服务 |

### 6.3 注册改造

当前注册逻辑在 `SysRegisterService.register` 中只调用 `userService.registerUser(sysUser)`。

P2 改造步骤：

1. 注册用户前继续校验用户名、密码和验证码。
2. 注册用户时设置默认角色为 `volunteer`，或在注册成功后插入 `sys_user_role` 关联。
3. `sys_user` 创建成功后，读取生成的 `userId`。
4. 创建 `vol_volunteer_profile`，默认 `audit_status = 0`。
5. 写入一条 `vol_audit_record` 初始记录，表示“提交注册待审核”。
6. 整个注册和档案创建过程使用事务，避免账号有了但档案缺失。

## 9. 验收标准

P2 完成需要满足以下场景：

1. 新用户可以注册并登录。
2. 注册成功后 `sys_user` 和 `vol_volunteer_profile` 同时存在。
3. 新志愿者默认状态为待审核。
4. 用户端个人中心能看到并维护志愿者档案。
5. 管理员能在志愿者管理页看到待审核用户。
6. 管理员通过审核后，志愿者状态变为通过。
7. 管理员驳回时必须填写原因，用户端可以看到驳回原因。
8. 管理员禁用志愿者后，用户端展示禁用状态。
9. 每次审核或禁用操作都会写入 `vol_audit_record`。
10. P3 报名接口可以通过服务方法判断志愿者是否审核通过。
