# P4 二维码签到签退与服务记录实施方案

## 1. 阶段目标

P4 的目标是完成志愿者从“报名通过”到“现场参与并形成服务记录”的业务闭环。

本阶段只做以下内容：

1. 管理端为活动生成签到二维码和签退二维码。
2. 志愿者通过二维码入口完成签到和签退。
3. 系统校验报名通过、二维码有效、时间窗口、重复签到和未签到签退等规则。
4. 签退成功后自动生成服务记录。
5. 系统按签到和签退时间计算服务分钟数。
6. 用户端可以查看个人服务记录和累计时长。

本阶段不做统计图表、批量导出、通知中心、证书生成、动态二维码刷新、定位签到或复杂防代签机制，这些放到 P5 或扩展功能。

## 2. 前置条件

P4 依赖 P3 已完成的能力：

1. 活动已经可以创建、发布和浏览。
2. 志愿者已经可以报名活动。
3. 管理员已经可以筛选报名人员。
4. P4 只允许 `vol_activity_signup.status = 1` 的报名记录进入签到签退流程。

当前可复用的验收数据：

| 数据 | 说明 |
| --- | --- |
| `P3-H闭环验收活动` | 已发布，`approved_count=1` |
| `p3g_demo_volunteer` | 已审核通过志愿者 |
| `P3-H闭环验收活动` 报名 | 已筛选为通过，可作为 P4 签到资格验证数据 |

## 3. 数据模型

### 3.1 活动二维码令牌表 `vol_activity_qr_token`

用于保存管理端生成的二维码令牌。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint PK | 主键 |
| `activity_id` | bigint | 活动 ID |
| `token` | varchar(128) | 随机令牌，唯一 |
| `action_type` | varchar(16) | `checkin` 签到，`checkout` 签退 |
| `expire_time` | datetime | 令牌过期时间 |
| `status` | tinyint | `0有效 1失效` |
| `create_by` | varchar(64) | 创建人 |

## 4. 状态定义

### 4.1 二维码令牌状态

| 值 | 名称 | 说明 |
| --- | --- | --- |
| `0` | 有效 | 可被扫码使用 |
| `1` | 失效 | 管理员停用或过期后不可使用 |

### 4.2 签到记录状态

| 值 | 名称 | 说明 |
| --- | --- | --- |
| `0` | 已签到 | 已签到但未签退 |
| `1` | 已签退 | 已完成签退，可生成服务记录 |
| `2` | 异常 | 缺少签退或规则异常 |
| `3` | 人工确认 | 管理员人工处理后的记录 |

### 4.3 服务记录状态

| 值 | 名称 | 说明 |
| --- | --- | --- |
| `0` | 待确认 | 已生成但等待管理员确认 |
| `1` | 有效 | 计入累计服务时长 |
| `2` | 异常 | 不自动计入 |
| `3` | 作废 | 管理员作废 |

P4 首版默认签退成功后生成 `status=1` 的有效服务记录；人工确认、异常集中处理和导出在 P5 扩展。

## 5. 业务规则

### 5.1 二维码规则

1. 二维码内容只包含前端扫码地址和随机 token，不直接暴露活动 ID、用户 ID 或操作类型。
2. 同一个活动可分别生成签到 token 和签退 token。
3. 重新生成同类型 token 时，旧 token 标记为失效。
4. token 必须有过期时间。
5. token 过期或失效后，扫码接口必须拒绝。

二维码地址建议：

```text
http://localhost:8088/#/scan?token=<token>
```

### 5.2 签到规则

1. 当前用户必须登录。
2. 当前用户必须有该活动的报名记录。
3. 报名状态必须为 `1` 通过。
4. 活动状态必须为已发布。
5. 签到 token 必须有效且 action_type 为 `checkin`。
6. 同一活动同一志愿者不能重复创建有效签到记录。
7. 默认允许签到时间为活动开始前 30 分钟至活动结束时间。

### 5.3 签退规则

1. 当前用户必须登录。
2. 当前用户必须已完成签到。
3. 签退 token 必须有效且 action_type 为 `checkout`。
4. 不能重复签退。
5. 签退时间必须晚于签到时间。
6. 默认允许签退时间为活动开始后至活动结束后 60 分钟。
7. 签退成功后自动生成服务记录。

### 5.4 服务时长规则

计算规则：

```text
原始服务分钟数 = 签退时间 - 签到时间
计入服务分钟数 = min(原始服务分钟数, 活动 max_service_minutes)
```

规则说明：

1. 原始服务分钟数小于等于 0 时，服务记录标记为异常。
2. 活动未配置 `max_service_minutes` 时，直接使用原始服务分钟数。
3. 有效服务记录生成后，更新 `vol_volunteer_profile.total_service_minutes` 和 `service_count`。
4. 服务记录必须能追溯到原始签到签退记录。

## 9. 验收标准

P4 完成需要满足以下场景：

1. 管理员能为已发布活动生成签到二维码和签退二维码。
2. 游客或未登录用户扫码会被引导登录。
3. 未报名用户扫码签到被拦截。
4. 报名未通过用户扫码签到被拦截。
5. 报名通过用户可以签到。
6. 重复签到不会生成第二条有效签到记录。
7. 未签到用户不能签退。
8. 已签到用户可以签退。
9. 重复签退不会生成第二条服务记录。
10. 签退成功后自动生成服务记录。
11. 服务时长按分钟计算，并受活动 `max_service_minutes` 限制。
12. 志愿者累计服务时长和服务次数随有效服务记录更新。
13. 用户端服务记录页可以展示个人服务记录和累计时长。
14. 管理端服务记录页可以查询活动服务记录。
